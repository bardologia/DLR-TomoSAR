# DLR-TomoSAR exhaustive audit report

**Date: 2026-08-02**

## Executive summary

Twenty Opus auditors swept the DLR-TomoSAR repository (pipelines, models, configuration, tools, webui, tests, scripts, docs). Of 292 raw findings, 171 survived independent adversarial verification against source, 79 were refuted, and 42 exceeded the verification budget. One finding is critical: cross-validation orchestration and its workers disagree on run-directory naming (`pipelines/cross_validation/stages.py:22-25` versus `pipelines/cross_validation/workers.py:115-126`), which silently disables CV inference, defeats resume, and makes the fold report raise on the default backbone configuration. Four other defects change or destroy results rather than merely degrading them: JEPA/profile-autoencoder inference derives the Gaussian count from an embedding width instead of the persisted `n_gaussians` (`pipelines/backbone/inference/loader.py:214`); checkpoint and resume-state writes are non-atomic, so a kill mid-write costs an entire training run (`tools/training/checkpoint.py:169`); the reach experiment's capacity match is computed at the registry default K=2 rather than the trained K (`pipelines/backbone/training/experiments.py:444`); and `FeatureSampler.features_at` treats every rank-4 activation as NCHW, so ConvNeXt layer probes and CKA produce wrong numbers today with no configuration change required (`pipelines/backbone/inference/layer_probes.py:83`). Two knobs exposed in the launch form never reach the code they claim to control (`snapshot_every_n_epochs`, `pipelines/shared/config/config_factory.py:92`), and the web console accepts an arbitrary interpreter path from an unauthenticated POST body and executes it (`webui/request_router.py:566`). Beyond individual defects, the dominant health themes are a fork of the shared training loop for the unrolled family, a god-object HTTP router, and systematic copy-paste across model libraries, monitors, and test scaffolding.

## Critical

### `pipelines/cross_validation/stages.py:22-25`, `:53-56`: Fold orchestration and fold workers use different run directories

`FoldTrainingStage` and `FoldInferenceStage` build their work items from `FoldNaming.name(index)` and derive every completion, resume, and log path as `stage_dir / item`, i.e. `<run>/folds/fold_0/seed1`. The workers resolve the run directory through `CrossValidationWorker.fold_run_name` (`pipelines/cross_validation/workers.py:115-126`), which prefixes the `RunNaming` training tag for `training_type` in `{backbone, jepa}`. On the default configuration the real directory is `<run>/folds/resunet-conv-hungarian-K_5-hv-A-param_l1_1-covariance_match_0.05-coherence_resyn_0.05-cosine_curve_0.05_fold_0/seed1`, and `CompletionMarker.stamp` is written there (`tools/training/trainer.py:487`).

Four consequences follow on the shipped defaults (`training_type='backbone'`, `seeds=[0..4]`, `resume=True`). `QueuedInferenceStage._training_complete` (`tools/orchestration/stages.py:161`) never finds a marker, so every fold and split is reported SKIPPED and cross-validation inference never runs. `QueuedTrainingStage._is_complete` (`tools/orchestration/stages.py:82`) never finds one either, so resume retrains every fold from scratch. The GPU queue creates `folds/fold_0/seed1/worker.log` (`tools/orchestration/gpu_queue.py:316`), so `FoldCollector` collects those log-only directories as extra empty folds and `CrossValidationReport._require_all_folds` (`cv_report.py:61`) raises because it sees `2*n_folds` records. Finally `training_results.json` is keyed `fold_0/seed1` while collected record names carry the tag, so `record.training_result` is always `{}` and every fold reports PARTIAL with duration `None`.

Only `training_type='profile_autoencoder'` is coherent, because `fold_run_name` returns the bare fold name there. The tests never exercise the divergence: `tests/cross_validation/test_stages.py:122` and `test_workers.py:39-40` build directories literally named `fold_0`. The tag prefix was introduced in commit 9965cd1 without updating the stage side. Sibling harnesses do not diverge: patch sweep passes the unit name straight through as `run_name` (`pipelines/patch_sweep/workers.py:46`) and benchmark uses `SeedExpandedStage.unit_base` for both.

Fix: derive the stage item and path from the same `fold_run_name` helper the workers use (or drop the prefix from the worker and record the model tag in run metadata), and add a regression test that stamps completion through the worker's own naming and asserts the stage observes it.

## Major

### Model correctness and analysis outputs

#### `pipelines/backbone/inference/loader.py:214`: Gaussian count derived from output width, ignoring the persisted `n_gaussians`

`RunLoader.load` computes `n_gaussians = out_channels_total // 3` and never reads `run_summary["n_gaussians"]`, although `save_run_summary` (`pipelines/shared/config/run_metadata.py:87-101`) persists that value and both the backbone (`pipelines/backbone/training/pipeline.py:212`) and JEPA (`pipelines/jepa/training/pipeline.py:259`) pipelines write it correctly. No reader in the repository consumes the field; the loader also has `dataset_config.n_gaussians` in scope from `dataset_creation_config.json` and ignores that too. The unrolled loader does the correct thing (`pipelines/unrolled/inference/loader.py:153`).

The failure surfaces through JEPA. A JEPA run coupled to a profile autoencoder writes `out_channels = autoencoder_cfg.embedding_dim` (`pipelines/jepa/training/pipeline.py:249,259`), and `JepaRunLoader` inherits `load` unchanged, so the derived K is `embedding_dim // 3`. That value drives the ground-truth channel selection in `PatchDataset` and becomes `run.n_gaussians` in `JepaCurvePredictor._forward_pass` (`pipelines/jepa/inference/predictor.py:14,29-34`) and `JepaEmbeddingEvaluator._gt_curves` (`pipelines/jepa/inference/embedding.py:22-28`). Two regimes result. With the shipped default `embedding_dim = 24` (`configuration/architectures/profile_autoencoder.py:12`) and K=5, the derived value is 8 and `PatchDataset` aborts with a message blaming the extraction configuration, which the user cannot act on because K is not settable at inference. When `embedding_dim // 3 < k_max` (for example `embedding_dim=12` with K=5), nothing raises: ground-truth curves are rebuilt from the first 4 Gaussians only and every JEPA curve metric, figure, and report number is silently wrong. `tests/jepa/test_inference.py` never drives `JepaRunLoader.load`; it builds fake runs with `n_gaussians` injected by hand.

Fix: read `run_summary["n_gaussians"]` (or `dataset_config.n_gaussians`) as authoritative and assert `out_channels == params_per_gaussian * n_gaussians` for the parameter-space loaders, converting the JEPA mismatch into an immediate, accurate failure.

#### `pipelines/backbone/inference/layer_probes.py:83`: Rank-4 activations are assumed NCHW, so ConvNeXt probe and CKA numbers are wrong

`FeatureSampler.features_at` unpacks `_B, C, h, w = maps.shape` (line 78), discards `_B`, and indexes `maps[b, :, fi, fj]` with `b` drawn from the input batch size. The only guard is `tensor.ndim != 4`. Two distinct violations follow.

The batch-dimension case: `models/blocks.py` window attention folds windows into the batch, so the leaf `attention.attention_dropout` in `swin_unet` emits `(batch_windows, num_heads, seq, seq)`. Measured with B=2 and a 4x64x32 input, `encoder_stages.0.blocks.0.attention.attention_dropout` has shape `(12, 2, 49, 49)`; because folding can only multiply the batch, `maps[b]` is always a legal index and the mis-sampling is silent. Whether such a layer lands in the selection depends on `max_layers`; with `LayerProbeConfig.max_layers = 20` or `CkaConfig.max_layers = 16` it does.

The layout case requires no configuration change and is worse. `ChannelLayerNorm` and `ConvNeXtBlock` (`models/blocks.py:242-280`) run their `norm`, `fc1`, `activation`, and `fc2` leaves on channels-last tensors. With `convnext_unet` and the default `max_layers = 24`, the selected layer list contains `encoder_stages.0.blocks.0.fc1 -> (4, 64, 32, 192)` and `encoder_stages.3.blocks.0.activation -> (4, 8, 4, 1536)`. Here dim 0 is correctly B, but `C, h, w` are read as `(H, W, C)`: the report records `n_channels = 64` for a 192-channel layer and the sampled "features" are spatial rows at clipped, meaningless coordinates. Those values drive the reported R-squared, the "K most decodable at `<layer>`" claim in `layer_probes.md`, and the CKA heatmaps produced through the same helper (`pipelines/backbone/inference/representation_cka.py:175`). `tests/backbone_inference/test_layer_probes.py` exercises only a two-Identity NCHW toy network.

Fix: assert `maps.shape[0] == B` and reject or explicitly route non-NCHW rank-4 activations instead of treating every rank-4 tensor as a feature map.

#### `pipelines/backbone/training/experiments.py:444`: Reach capacity check sizes each arm at K=2 while training builds it at the dataset K

`ReachTrialPlanner._parameters` calls `get_backbone(rung["backbone"], in_channels=self.trials.in_channels, head=self.head, **sizing, **self._overrides(rung))` with no `out_channels`, so every arm is counted at the registry default of 6 channels, that is K=2. Training instead sets `out_channels = GaussianHead.total_channels(ppg, gaussian_cfg.n_default_gaussians)` from the dataset (`pipelines/backbone/training/pipeline.py:197-201`), and K comes from `param_extraction_meta.json`, so K=5 is routine. For `set_pred` (the default head, `configuration/training/backbone.py:227`) the output stage is K PixelMLPs sized on `embedding_channels`, so the parameter count depends on both K and the arm's very different width.

Measured with the repository's own code on the default reach rungs, patch (32,32), in_channels 9: with `set_pred`, K=2 gives cnn33 31,374,744 versus unet 31,047,530 (1.054 percent), while K=5 gives 31,721,787 versus 31,054,169 (2.150 percent). A concrete false pass: `local_cnn` features `[477]*8` deviates 0.213 percent at K=2 (accepted under the 1 percent `match_tolerance`) but 1.299 percent at K=5, so the arms actually trained are outside tolerance and the guard never fires. The mirror case also exists: `[474]*8` is rejected at 1.052 percent while the trained K=5 pair matches to 0.035 percent. The asymmetry is clearly unintended because `_validate` (`experiments.py:433-434`) explicitly guards `in_channels` with the message that "training builds every arm at the dataset width, so the capacity check would count the wrong first layer". The same omission exists in `DualReachTrialPlanner._parameters` (`pipelines/dual/training/experiments.py:57-77`). All nine reach tests pass `head="conv"` and never vary K.

Fix: thread the resolved `out_channels` (`ppg * n_default_gaussians`) into both planners and validate it the way `in_channels` is validated.

#### `pipelines/backbone/inference/paper_figures.py:48-55`, `configuration/diagnostics.py:384`: Paper figure pack silently drops every vector figure

`PaperFigurePackConfig.patterns` matches only `*.png`, while `PlotBase._save` (`tools/reporting/plotting.py:99-101`) rewrites the extension to `.pdf` whenever `PlotBase.style == "paper"` and the figure has no raster axes. That upgrade is intentional and test-pinned (`tests/reporting/test_plotting.py:437`). Consequently, under `figure_style=paper`, `profiles/`, `param_scatter/`, and `stratified/` become entirely `.pdf` and `data_consistency/` becomes partly `.pdf`. Because `pixel_maps/*.png` still matches, `_collect_run` never raises: the pack ships only the raster maps.

Reproduced by running the collector against a run tree shaped as paper-style inference leaves it: packed output was `['run_a__pixel_maps__mse.png', 'run_a__pixel_maps__r2.png', 'run_a__data_consistency__coherence_error_map.png']`, with every `.pdf` dropped, no error, and a manifest reporting success. The workflow that triggers this is the one the repository instructs (`paper_figures.py:74`, `main/analysis/export_paper_figures.py:17`, `webui/script_catalog.py:198` all tell the user to run inference with `figure_style=paper` first). Nothing in the repository globs `*.pdf`, and `tests/backbone_inference/test_paper_figures.py` writes only `.png` fixtures.

Fix: make the patterns extension-agnostic or add explicit `.pdf` entries, and have `_collect_run` verify each pattern individually so an empty pattern fails loudly.

#### `webui/ab_autopsy.py:133-157`: Autopsy plots run B's curve against A's elevation axis without validating B

`AbAutopsy.profile` bounds-checks `az`/`rg` against `pred_a` only (line 141) and builds `x_axis` from run A's `metrics.json` sampled at `pred_a.shape[0]` (line 145), then slices `pred_b` at line 153 with no shape or axis validation. `webui/static/js/autopsy.js:113-117` draws `data.a`, `data.b`, and `data.gt` against the single `data.x_axis`, so a run B trained or inferred on a different elevation grid is rendered on the wrong axis. The elevation axis is genuinely per-run: `x_axis = GaussianAxis.build(gaussian_cfg.x_min, gaussian_cfg.x_max, layout.profile_length)` (`pipelines/backbone/training/pipeline.py:68`), persisted in the checkpoint and reloaded at `pipelines/backbone/inference/loader.py:114`. `compare()` validates only the two-dimensional `pixel_mse` shapes (line 112), which says nothing about the elevation dimension.

The sibling cross-run comparison performs exactly the missing checks: `webui/cube_explorer.py:198-204` compares full shapes and applies `np.allclose` to the elevation axis, erroring with "comparison cube covers a different elevation axis". A shorter `pred_b` is compressed onto A's grid; a longer one indexes past the axis end, giving NaN coordinates and a silently truncated path. `tests/webui/test_ab_autopsy.py` builds both stamps with identical elevation length and axis bounds.

Fix: validate `pred_b.shape` against `pred_a.shape` and compare B's own `x_axis_min`/`x_axis_max` against A's, mirroring `cube_explorer.py:198-204`; also add `IndexError` to the caught tuple at line 156.

### Configuration reaching the code it claims to control

#### `pipelines/shared/config/config_factory.py:92-103`: `snapshot_every_n_epochs` never reaches the trainer

`TrainingQueueConfig.snapshot_every_n_epochs` (`configuration/training/general/run.py:49`) is claimed by the webui launch form (`webui/launch_layout.py:217`), documented in `webui/config_descriptions.json`, and referenced by user-facing instructions in `main/analysis/animate_training.py:17`, `webui/script_catalog.py:188`, and `pipelines/backbone/inference/training_evolution.py:57`. `ConfigFactory.training_trainer_config` is the only production construction site for `TrainingLoopConfig` (all other constructions are in tests), and its exhaustive keyword list omits this field, so the runtime value stays at the `TrainingLoopConfig` default of 0 (`configuration/training/general/runtime.py:34`). `BaseTrainer._maybe_snapshot` (`tools/training/trainer.py:363-374`, called per epoch at line 467) returns immediately.

A repository-wide grep across Python, JavaScript, and JSON registries finds no other writer. Every entry routed through this factory is affected: backbone, dual, JEPA, both autoencoders, benchmark, tuning, cross-validation, patch sweep, and batch probe (JEPA and the autoencoders inherit the already-defaulted loop config through `TrainerConfig.inherit_shared_from`). Setting the knob trains normally but writes no `checkpoints/epoch_XXXX.pt`, and `main/analysis/animate_training.py` then fails with an instruction the user cannot satisfy. No test asserts the propagation.

Fix: add `snapshot_every_n_epochs = training.snapshot_every_n_epochs` to the `TrainingLoopConfig` construction, plus a test asserting the entry value round-trips into `trainer.config.training`.

#### `webui/launch_layout.py:890`, `:901`, `:897`, `:968`, `:962-963`, `:1068-1069`: Multi-type launch pages expose panels the selected pipeline ignores

The `benchmark`, `cross_validate`, and `tune` pages are `type_tab` pages where `training_type` selects an entirely different pipeline. Several sections are correctly gated with `when` (size-match, ae-loss, jepa, tune's loss), but these are not, despite being unread by the non-backbone pipelines: benchmark "Input channels" (`BenchmarkConfig.input` is consumed only by `TrainingWorker._run_backbone`, `pipelines/benchmark/workers.py:154`; JEPA builds its dataset from the hardcoded `InputConfig.full_stack()` at `pipelines/shared/config/config_factory.py:29-30`), benchmark "Loss", benchmark "Max-batch probe" (`runs_max_batch()` is `training_type == "backbone"`, `configuration/benchmark/general.py:116`), cross-validate "Loss" (`cv.curriculum` is applied only in `FoldTrainingWorker._run_backbone`), and the cross-validate and tune Normalization/Augmentation panels on the profile-autoencoder tab (`ProfileAeEntryConfig` has neither field). Benchmark's own Normalization, Augmentation, and Geometry panels are dropped on the Profile AE tab for the same reason (`pipelines/benchmark/workers.py:60-72`).

Because the fields exist on the entry dataclass, `LaunchLayout._validate` is satisfied and nothing errors; the values are simply discarded. `StagedPipeline.__init__` then writes `ConfigCli.save_resolved(config, pipeline/resolved_config.json)` (`pipelines/shared/orchestration/staged_pipeline.py:24`), so the dropped values are archived into the run record, producing an artifact that claims, for example, `input.use_interferograms=false` for a JEPA benchmark trained on the full stack. The unrolled pipeline handles the analogous case with an explicit `_warn_inert_augmentation` (`pipelines/unrolled/training/pipeline.py:100-105`, tested), showing the intended handling is a loud warning.

Fix: gate the affected panels with `when` clauses as the size-match and ae-loss sections already do, or add `_warn_inert_*` guards to the non-backbone workers.

#### `configuration/architectures/backbone.py:461`: SwinUNet tuning offers `embedding_dim` values the model rejects

`SwinUNetConfig.num_heads` is fixed at `(2, 5, 10, 20)` (line 425) and is not tunable; `SwinUNet.__init__` computes stage dims as `embedding_dim * 2**i` and raises unless each is divisible by its head count (`models/backbone/swin_unet.py:309-315`). Stage 1 therefore requires `embedding_dim` to be a multiple of 5. Instantiating each tunable choice confirms this: 48 raises ("Stage 1: embedding dim (96) must be divisible by num_heads (5)"), 80 succeeds, 96 raises, 128 raises. Three of four categorical values are unbuildable, so the search dimension is effectively a single point.

`Tuner.run` calls `study.optimize(...)` with no `catch=` (`pipelines/tuning/tuners.py:151`); a live Optuna run in the same environment confirms the ValueError is recorded as a FAIL trial and then re-raised out of `optimize`, killing the worker process at its first offending sample (roughly 75 percent chance on the first trial) and losing that worker's remaining budget. `swin_unet` is in `BACKBONE_CONFIG_REGISTRY`, `TuningEntryConfig.skip_models` defaults to `[]`, and `TuningScheduler._model_keys()` enumerates the whole registry, so a default sweep reaches it. The same broken space is reached through `JepaTuner` (`pipelines/tuning/workers.py:96-105`). `tests/models_backbone/_helpers.py:12` overrides `num_heads` to `[1, 2, 4, 8]`, so the default head list is never combined with the tuned embedding dims.

Fix: restrict the choices to multiples of 5 that keep every stage divisible, or make `num_heads` derived from `embedding_dim`; independently, pass `catch=(ValueError,)` so invalid samples do not kill workers.

#### `configuration/architectures/backbone.py:726`, `:1181`: Tuple-valued categorical choices break Optuna's RDB round-trip

`DeepLabV3PlusConfig.atrous_rates` and `U2NetLiteConfig.rsu_heights` declare sequence-valued choices under `"type": "categorical"`, which `ParamSampler.sample` forwards to `trial.suggest_categorical` (`pipelines/tuning/tuners.py:25`). Every other sequence-valued parameter in the file uses the `indexed_categorical` form that exists precisely to avoid this. Tuning uses SQLite RDB storage (`pipelines/tuning/pipeline.py:30`), which serialises the distribution to JSON; the tuples return as lists.

Reproduced with Optuna 4.8.0 and SQLite storage: the first process works but emits `UserWarning: Choices for a categorical distribution should be a tuple of None, bool, int, float and str for persistent storage`; a second process loading the same study raises `ValueError: CategoricalDistribution does not support dynamic value space` from `check_distribution_compatibility`. Because Optuna caches distributions per process, the first worker succeeds throughout while every concurrent worker in the per-GPU fan-out, and every worker in a `--resume` run, fails on its first `suggest_categorical` and on all subsequent trials. Values also round-trip through the database as lists, so `BestConfigWriter` writes `"atrous_rates": [2, 4, 8]`.

Fix: change both entries to `indexed_categorical`.

### Web console

#### `webui/request_router.py:566`: Interpreter path taken verbatim from the request body and executed

`/api/run`, `/api/saved-runs`, and `/api/tensorboard/start` accept an arbitrary `interpreter` string from the POST body and pass it unvalidated to `ProcessManager.launch/enqueue`, where `process_manager.py:190` builds `argv = [record["interpreter"], "-u", str(entry["path"]), *entry["args"]]` and `Popen` executes it. Every other launch input is validated: the script key against `ProjectPaths.SCRIPT_DIRS` (`request_router.py:563`) and override names against `OVERRIDE_NAME` (`process_manager.py:299`). `ProjectPaths.discover_interpreters()` exists (`project_paths.py:145`) but is used only to populate the UI dropdown. A cleaner execution sink exists at `webui/script_config_resolver.py:133`, which runs `[interpreter, "-c", self.BOOTSTRAP, ...]` and is reachable from `POST /api/tensorboard/start` (`request_router.py:734-735`).

There is no authentication and no Origin, Referer, or Host check, and `_read_json` ignores Content-Type (`request_router.py:891`), so a cross-site `text/plain` POST is a CORS simple request and is delivered and executed regardless of the wildcard CORS header. (The wildcard header at `request_router.py:917` additionally lets the attacking page read the response, but is not what permits the write.) The server binds 127.0.0.1 and is already an unauthenticated launcher for the repository's scripts, which caps the marginal risk; control of `argv[0]` plus the `-c` sink is nonetheless an escalation. The frontend only ever sends values chosen from the discovered list (`launch.js:606-607`, `ablation.js:130`, `console.js:391-392`).

Fix: reject any interpreter not present in `ProjectPaths.discover_interpreters()`. This breaks no legitimate flow.

#### `webui/model_probe.py:57`: Model Probe passes `WebLogger` into `RunLoader`, so the Microscope tab can never load a run

`ModelProbe._load_worker` calls `RunLoader(Path(run_path), logger=self.logger)` where `self.logger` is the `WebLogger` created in `web_ui_server.py:68`. The first statement of `RunLoader.load()` is `self.logger.section(...)` (`pipelines/backbone/inference/loader.py:200`), followed by `subsection` and `kv_table`; the same logger is passed into `Stats.load`, `Layout`, and `Cropper`. `WebLogger` (`webui/web_logger.py`, 51 lines) defines only `info/ok/warning/error/muted/banner` with no `__getattr__` fallback. Executed directly, the call raises `AttributeError: 'WebLogger' object has no attribute 'section'` before any filesystem access, so it fails identically for every path. The status error is formatted as `f"{type(error).__name__}: {error}"` (`model_probe.py:104`), so the frontend displays the AttributeError text, which reads as a probe bug rather than a wiring bug. `POST /api/probe/load` (`request_router.py:655`) is the tab's only entry point.

`tests/webui/test_model_probe.py` never calls `start_load`/`_load_worker`; all three tests assign `probe.loaded` by hand and use a `_SilentLogger` stub with `__getattr__`.

Fix: construct a real `tools.monitoring.logger.Logger` inside `_load_worker` for the pipeline call chain, or extend `WebLogger` with `section`/`subsection`/`kv_table`; add a test that drives `_load_worker` against a fixture run directory.

#### `webui/gpu_schedule.py:270`: A blocked pool shrink is recorded as applied and never retried

`tick()` writes the new phase into `self.applied[job_id]` before `_cross` runs, and `_cross` records `withheld` and returns early when no GPU of the target pool is grantable. The only recovery path is `sweep()`, and `_claim` (line 374) computes `sorted(set(current) | set(freed))`, a union that can only grow a pool. For a growing transition (weekday to night or weekend) that is correct; for a shrinking transition it is not. Driving the real `GpuSchedule` against the repository's own stubs, a job live on `[0,1,2,3]` over the weekend with GPUs 2 and 3 held by another user and `tick(Monday 09:00)` produces: writes `[]`, pool `[0,1,2,3]`, `applied={'job1': {'phase': 'weekday', 'withheld': [2,3]}}`; after 2 and 3 free and `sweep()` runs, still pool `[0,1,2,3]` with `withheld` drained. The job holds the full night pool through the workday, which is exactly what the weekday schedule exists to prevent, and no log line reports the lost shrink after the initial warning. The loss is not confined to greedy mode: with greedy off or during a charity nap, `sweep` returns at line 391 and the shrink is equally unrecoverable. A `set_gpus` failure at line 248 with an empty `withheld` list is likewise lost until the next phase boundary. Existing tests cover only the growing direction (`tests/webui/test_gpu_schedule.py:250`).

Fix: latch `applied[job_id]["phase"]` only after `_cross` reports success so the next tick retries, and have `sweep` re-derive the pool from `gpus_for(record["phase"])` intersected with availability rather than unioning with the current pool.

### Robustness and resource use

#### `tools/training/checkpoint.py:169`, `:50`: Checkpoint and resume-state writes are not atomic

`TrainerState.save` rewrites `last.pt` in place at the end of every epoch (called unconditionally at `tools/training/trainer.py:466`) and `Checkpoint.save` rewrites `best_model.pt` on every improvement, both with a bare `torch.save` onto the destination path. `torch.save` opens the destination `wb`, truncating it, then streams a payload containing model, optimizer, EMA shadow, and RNG states, so death mid-write leaves a truncated file rather than the previous good one.

There is no second copy. Grepping for `last.pt` finds only the constant and a cleanup list; `TrainerState.restore` (`checkpoint.py:172-195`) is the sole resume reader and hard-fails on a bad file. `best_model.pt` cannot substitute because `Trainer.capture_state` (`trainer.py:211-216`) stores only `{epoch, params, x_axis}`. The kill scenarios are designed-for, not hypothetical: `webui/process_manager.py:719/733` sends SIGTERM then SIGKILL after an 8 second grace, `webui/resource_watchdog.py:84` kills on RAM pressure, and `tools/orchestration/gpu_queue.py:220-236` terminates and kills workers past the deadline while logging "terminated N workers, resume with --resume". A truncated `best_model.pt` additionally breaks every downstream consumer: JEPA training loads the autoencoder checkpoint (`pipelines/jepa/training/pipeline.py:49,58,244`), and comparison and patch-sweep reporting rglob for it (`pipelines/shared/comparison/trial_collection.py:122`, `pipelines/patch_sweep/report.py:66`).

The repository already implements the atomic pattern for JSON (`tools/data/io.py:20-31`, used at `gpu_queue.py:50,191` and `tuners.py:68`); it was never applied to the torch payloads, which take seconds to write.

Fix: write to `path.with_suffix('.pt.tmp')` and `os.replace` in `TrainerState.save`, `Checkpoint.save`, `Trainer._maybe_snapshot` (`trainer.py:372`), and `pipelines/unrolled/training/trainer.py:159`.

#### `pipelines/backbone/inference/metrics.py:235`: Every slice of every axis is materialised as float64 before any SSIM work is submitted

`_enqueue_tasks` appends `p_sl.astype(np.float64)` and `r_sl.astype(np.float64)` for every index, and the pipeline passes all elevation, range, and azimuth indices (`pipeline.py:108-119`). `astype` copies unconditionally, and the axis-1 and axis-2 slices are non-contiguous views, so no copy is elided. The whole `tasks` list is resident before `ProcessPoolExecutor` is created at line 198, at 48 bytes per cube element (2 arrays x 3 axes x 8 bytes). With the default test split (azimuth 14564-16000 = 1436 lines, range 500-4000 = 3500 samples) and 150 elevation bins (confirmed from `test_data/data/tomogram_full.npy`, shape `(150, 1000, 500)`), the float32 cube is about 3.0 GB and `tasks` holds about 36 GB. `_slice_ssim` is entered three times per run (gt, norm, red), so this is a repeated peak. The float64 upcast is not required: `structural_similarity` accepts float32 and `data_range` is passed explicitly at line 243.

Fix: pass `(key, axis, index)` to workers and share the cube through fork-inherited or shared memory, or at minimum keep the native float32 and submit in bounded batches. Moving the cast into `_ssim_worker` alone only halves the peak.

#### `pipelines/backbone/inference/representation_cka.py:208`: CKA loads every selected run fully into memory at once

`CkaComparison.run` builds `runs = [self._load(run_dir) for run_dir in run_dirs]` before validating alignment or collecting any features, and the list stays referenced for the whole method. `RunLoader._build_dataset` hardcodes `cropper.load_split(region, load_tomogram=True)` (`pipelines/backbone/inference/loader.py:143`, the only such call site in the repository), and `Cropper._load_tomogram` (`pipelines/backbone/dataset/spatial.py:84-86`) materialises the whole split cube in RAM. CKA never touches it: `_collect` uses only `run.model.module` and `run.loader`, and `_validate_alignment` only `split_region`/`dataset_config`.

At the project's default crop the test split is roughly 5.0e6 pixels; at 300 elevation bins that is about 6.0 GB per run of unused tomogram, roughly 90 percent of each `Run`'s footprint, while only about 32 patches are ever consumed (`batch_size 4 x max_batches 4`). `_select_runs` falls back to `selector.all()` whenever stdin is not a tty (lines 113-116), which is exactly how the webui launches it (`webui/script_catalog.py:170`), and `RunSelector.all()` rglobs every `best_model.pt` under the runs directory. The eager list also means a misaligned-runs `ValueError` at line 209 is paid only after every run has been loaded.

Fix: add a `load_tomogram` parameter to `RunLoader.load` (default False, True only for the backbone path that populates `Run.full_curves`), and load, collect features, and release one run at a time.

#### `pipelines/backbone/inference/predictor.py:197-213`: All rendered patch curves for the whole split are held in RAM before stitching

`_compute_metrics` submits one task per batch for the entire dataset in a single dict comprehension and stores every completed payload in `results[idx]`, which is returned intact and consumed only in `_stitch_results` (line 267), staying alive through `_finalize_results` while the output cubes are materialised. Each payload holds `pred_curves` and `gt_curves` at full patch resolution. With the standard (64,32) patch and (32,16) stride the patch grid oversamples by 4, so the resident curve payload is 8 stitched-cube-equivalents, plus roughly 2 more once `_finalize_results` materialises the pred and gt cubes while `results` is still referenced.

The intent to bound memory is explicit elsewhere in the same file: `CubeStitcher`/`SelectStitcher` accept `memmap_path` and `save_cubes` defaults to True, so the single-cube accumulators go to disk while the eight-cube worker buffer stays in RAM. Incremental consumption is available: `futures[fut]` already yields the task index and `all_indices[i]` gives the patch indices. The same pattern is inherited by `JepaCurvePredictor` (`pipelines/jepa/inference/predictor.py:14-42`).

Fix: stitch inside the `as_completed` loop and drop each result after `add_patch`, or bound in-flight futures to a small multiple of `cpu_workers`.

#### `pipelines/profile_autoencoder/inference/pipeline.py:60`: Autoencoder inference holds the whole split and then duplicates it in float64

`AeReconstructionPredictor.run_inference` (`pipelines/autoencoder_common/inference/predictor.py:37-56`) concatenates every batch into three whole-split float32 arrays (gt, pred, embeddings), and `AeMetricsBase.__init__` (`pipelines/autoencoder_common/inference/metrics.py:13-17`) immediately makes float64 copies of all three. Both sets stay resident because `ProfileAeInferencePipeline.run` holds `result` and `metrics_obj` simultaneously and `ProfileAePlots.compose` consumes `result.gt`/`result.pred`/`result.embeddings` afterwards.

At production defaults the test region is 1436 x 3500 = 5.0e6 pixels with `pixel_subsample = 1.0`, and the profile length equals the tomogram bin count (300 in the shipped preprocessing twin), giving roughly 4.8 GB per float32 array and 9.6 GB per float64 copy. Peak is higher still because `_physical_errors`, `_normalized_errors`, `_shape_errors`, and `_power_errors` each allocate further full-split float64 temporaries. The inference scheduler runs one worker per GPU, so this peak multiplies. `tests/ae_inference/test_metrics.py` checks values only on tiny synthetic arrays.

Fix: accumulate metric sums streaming over batches, or compute the metrics in float32 and release the float32 result before upcasting.

#### `pipelines/processing/param_extraction/metrics.py:152`: Fit-metrics stage loads the whole tomogram into RAM

`FittingMetricsCalculator._load_tomogram` calls `np.load` with no `mmap_mode`, so the entire complex64 tomogram enters RAM, and `np.abs(...)` allocates a full float32 cube while the complex cube is still referenced. Every other component of the same subsystem memory-maps this file: `SigmaFittingExtractor._prepare_data` (`sigma/extractor.py:117`) and `ExampleFitPlotter._extract_pixel_profiles` (`plots/examples.py:66`). `ContrastEstimator.run` (lines 39-46) then loops over range chunks applying `np.abs(...)` again to data that is already real, so its chunking is pure overhead. `ProfilePreprocessor.apply` allocates another full-size copy, `_compute_r2_map` allocates `pred` at full cube size, and `R2.pixel_map` (`tools/metrics/scoring.py:57-63`) promotes `(ref - ref_mean)` and its square to full-size float64 because the mean is computed with `dtype=np.float64`. Peak is roughly 24 bytes per cube element. At the repository default crop (15000 azimuth x 3500 range x 150 bins) that is about 63 GB complex on disk and a transient peak near 190 GB. The whole cube is re-loaded once per extraction trial (the default `fit_modes` list has three entries).

Fix: open with `mmap_mode="r"` and drive contrast, preprocessing, and R-squared accumulation through the same range-chunk loop the extractor already uses, accumulating `ss_res`/`ss_tot` per chunk.

#### `webui/system_monitor.py:464`, `webui/contention_monitor.py:270`: `smaps_rollup` read for every own process every 2 and 5 seconds

`ProcStats.attributed` reads `/proc/<pid>/smaps_rollup`, forcing a kernel page-table walk. `ActiveUsers._scan` calls it for every `/proc` entry on a 2 second loop and `ContentionMonitor._scan` does the same on a 5 second loop, with no cache, no throttle, and no sharing. The rollup is ptrace-gated, so other users' processes fall back to the cheap `statm` read; on a training box the expensive walks are therefore concentrated on exactly the multi-gigabyte jobs. Measured here (150 own pids, desktop-sized processes) one full pass costs 137 ms of `smaps_rollup` time, with a single 0.92 GB process taking 17 ms. At the two cadences that is roughly 10 percent of a core burned continuously, and the walk holds the target's mmap read lock for its duration. A third, uncited source of the same cost is `SystemMonitor._procs` (`system_monitor.py:130`), which calls `ProcStats.pss` on the top 30 processes on every `/api/system` request, polled at 250 ms by `home.js:156`.

Fix: add a short-TTL cache in `ProcStats`, or have one shared scanner feed all three call sites, refreshing the PSS value on a slower cadence than the cheap counters.

#### `webui/system_monitor.py:366`: Four monitors each shell out to `nvidia-smi`

There is no shared or cached GPU snapshot. `SystemHistory.sample_loop` runs `_gpu_devices()` every 0.5 s (2 spawns/s), `ActiveUsers.sample_loop` runs `gpu_occupancy()` every 2 s (1 spawn/s), and `GpuWatchdog._watch` runs it every 4 s (0.5 spawns/s), for a sustained 3.5 process spawns per second with no clients connected. Measured on this machine, the two queries cost 34.9 ms and 22.0 ms (20-run average, single GPU), roughly 11 percent of a core, scaling with device count on the four-GPU server. `/api/system` adds two more spawns per request, and `home.js:156` polls it every 250 ms, so an open home tab adds 8 spawns/s and each additional tab multiplies that again (the server is a `ThreadingHTTPServer`). The `GpuSchedule` contribution is negligible in the default configuration: `idle()` requires charity mode (disabled by default) and `busy()` runs only on phase transitions or the 600 s sweep.

Fix: put a short-TTL (about 0.5 s) cached `gpu_occupancy()`/`_gpu_devices()` behind a lock and have all consumers read it.

#### `webui/static/js/home.js:156`: `/api/system` polled at 4 Hz from every tab on every route

`StatusBoard.start()` installs `setInterval(() => { if (!document.hidden) this._poll(); }, 250)`. `StatusBoard` is constructed once at boot (`app.js:163-168`) and is never referenced by the router's `_onRoute`, which does provide enter/leave for other views, so the poll continues on every route even though the DOM it drives lives entirely inside `<section data-page="home">`. Server-side, `request_router.py:541` calls `SystemMonitor.snapshot()` with no cache or rate limit, forking two `nvidia-smi` processes per request and walking all of `/proc`. A `this._polling` re-entrancy guard caps the effective rate at `min(4 Hz, 1/RTT)`, giving roughly 6 to 8 forks per second per tab. `GpuCardSelect.load()` (`launch_widgets.js:4119`) also fetches the whole `/api/system` payload per picker instance merely to read `payload.gpus`.

Fix: gate the poll on the home page being active as `tensorboard.js` and `tomogram.js` do, slow it to about 1 Hz, and cache the snapshot server-side; the same TTL cache also removes the baseline sampler load described above.

**`pipelines/backbone/training/trainer.py:73-74`**: `ParamSampler` and `SlotVitals` copy `initial_loss_cfg.amp_zero_thr` (the warmup stage) into plain attributes that neither `CurriculumController.maybe_swap` nor `_on_state_restored` ever refreshes, while `Loss._param_term`, `_physical_errors`, `_match_params`, and `_occupancy` read the threshold live. **`tools/loss/param_loss.py:10`**: `ParamMatcher.ACTIVE_AMP_THR = 1e-3` is the class default, but training overrides it with `LossConfig.amp_zero_thr = 1e-4` (`configuration/training/general/loss.py:59`) at `pipelines/backbone/training/loss.py:158`, while the whole inference stack uses the 1e-3 constant. ## Organization and code health

Six themes account for the 30 organization findings and 7 convoluted-code findings.

### Theme 1: A forked training runtime

`UnrolledTrainer` (`pipelines/unrolled/training/trainer.py:23`) is a standalone 220-line loop duplicating what `tools/training/trainer.py::BaseTrainer` provides for every other family: optimizer construction, batch-size LR scaling, `Warmup`/`Scheduler` wiring, `WeightEma`, `VramReservation`, checkpointing, early stopping, and completion marking. The fork has already drifted: it hardcodes `use_amp = False` and never autocasts, has no `gradient_accumulation_steps`, no non-finite-loss guard, no `Tracker` or resource monitoring, no `TrainerState` resume, no `_maybe_snapshot`, no `GradientClipper` telemetry, and no `validation_frequency`. The unrolled resume gap documented above is a downstream consequence. Porting it onto `BaseTrainer` also requires giving `UnrolledEntryConfig` the optimizer, memory, resources, and early-stopping sub-configs.
